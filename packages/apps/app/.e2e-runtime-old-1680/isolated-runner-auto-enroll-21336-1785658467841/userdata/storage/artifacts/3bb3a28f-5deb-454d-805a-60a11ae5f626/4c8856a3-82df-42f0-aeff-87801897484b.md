# Dev Runtime Slowness — Investigation

**Date**: 2026-05-09
**Scope**: Why dev mode "excruciatingly slow"

## TL;DR

Autocomplete in `ChatPanel` re-fetches **all 4 sources** every render. Sources fan out to IPC handlers that shell out to git or walk disk. Plus every IPC pair (req+res) is logged to a separate sqlite DB **synchronously, no batching**. Diagnostics retention only runs on system idle ≥60s — dev session never idle → DB grows unbounded.

Result: **80 IPC/sec** + ~160 sync sqlite writes/sec just from autocomplete. Diag DB at **16.5 GB**, WAL at 3.4 GB.

- Tick only deletes when `getSystemIdleTime() ≥ 60s` (or 10s fallback after 4h MAX_PAUSE)
- Active dev session = never idle = never runs

## Root Cause #1 — Autocomplete fetch loop

**File**: `packages/domains/task-terminals/src/client/chat/autocomplete/useAutocomplete.ts:82-102`

```ts
useEffect(() => {
  void Promise.all(
    sources.map(async (src) => {
      const items = await src.fetch({ cwd: cwdRef.current })
      ...
    })
  )...
}, [sources, fetchCtx.cwd])   // ← `sources` reference unstable
```

**Chain**:
1. `ChatPanel.tsx:228` `useMemo([..., createCommandsSource(text => sendMessage(text)...)], [sendMessage])`
2. `sendMessage` declared as plain `const` in `useChatSession.ts:273` — new ref every render
3. → `sources` array reference changes every render
4. → effect re-fires → 4 IPC calls per ChatPanel render
5. ChatPanel re-renders constantly during active chat (timeline/state/inFlight updates)
6. Hidden tabs stay mounted → multiplies per open task tab

**Cost per fire**:
- `chat:listFiles` → spawns `git ls-files` subprocess (`files-scan.ts:26`)
- `chat:listSkills` → walks disk
- ~160ms per cycle, 4 IPC roundtrips, redundant data

## Root Cause #2 — IPC instrumentation = synchronous sqlite writes

**File**: `packages/domains/diagnostics/src/main/service.ts:345-416`

`instrumentIpcMain` wraps every `ipcMain.handle` registration. For each call:
- `ipc.request` event → `INSERT INTO diagnostics_events` (sync)
- `ipc.response` event → `INSERT INTO diagnostics_events` (sync)

No batching, no debouncing, no allowlist/denylist by frequency. At 80 autocomplete IPC/sec → **160 sync inserts/sec** on a 16 GB DB. WAL keeps growing because the high write rate prevents checkpoint completion.

## Root Cause #3 — Retention dead during dev

**File**: `packages/domains/diagnostics/src/main/retention.ts:96`

```ts
if (idle < threshold) {            // threshold = 60s (10s fallback)
  scheduleNext(deps, TICK_BUSY_MS)  // skip — try again in 30s
  return
}
```

Active dev → keystrokes/mouse → idle never crosses threshold → retention never runs → 200k cap never enforced → DB grows from 200k to 45M rows.

## Recommended fixes (sustainable)

Ranked by impact / effort:

1. **Cache autocomplete sources in main process** — listSkills/listAgents/listCommands/listFiles results don't change between keystrokes. Add LRU/time-window cache keyed on cwd, invalidate on file-watcher events. Or move the fetch into a `useEffect` with stable `cwd`-only dep + manual refresh.

2. **Stabilize `sendMessage` in `useChatSession`** — wrap in `useCallback` with deps `[opts.tabId]` (chat.send is module-level). Cuts source recreation. (Necessary but not sufficient — many other ChatPanel renders still cycle.)

3. **Batch diagnostics writes** — accumulate events in memory, flush every N ms or N events via single transaction. Cuts sync write rate ~100x.

4. **Skip ipc.request+response for high-frequency channels** — add `IPC_LOG_SKIP_CHANNELS` (mirroring existing `IPC_PAYLOAD_SKIP_CHANNELS`) for `chat:list*`, `git:isGitRepo`, `db:tasks:getSubTasks`, `db:artifactFolders:getByTask`, `db:taskTags:getForTask`. Or downgrade to `level:'debug'` and gate by `verbose`.

5. **Run retention on a wall-clock interval** — keep idle preference but force a tick after ~30 min regardless of idle so DB never exceeds 200k cap.

6. **Throttle `git:getResolvedCommitDag`** (300ms × 23k/hr) — cache + invalidate on `git:command` writes only. 

7. **Manual cleanup now**: stop app → `sqlite3 slayzone.dev.diagnostics.sqlite "DELETE FROM diagnostics_events; VACUUM;"` to recover ~20GB disk + reset WAL.
