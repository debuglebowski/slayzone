# @slayzone/server — Incremental Migration Intent

## Why

Today all backend logic lives inside the Electron main process. That couples
SlayZone to running on the user's machine. Goal: extract the backend into a
standalone `@slayzone/server` package that can run **anywhere** — on the user's
machine (default, embedded), on a remote VPS, in a container, on a hosted
multi-tenant service later.

Electron stays as the desktop shell + renderer. It just becomes one of several
ways to host the server.

## End state

```
┌────────────────────────────┐         ┌────────────────────────────┐
│  Renderer (React)          │         │  Renderer (React)          │
│  - tRPC client over WS     │         │  - tRPC client over WS     │
└────────────┬───────────────┘         └─────────────┬──────────────┘
             │ ws://localhost:PORT                   │ wss://host
             ▼                                       ▼
┌────────────────────────────┐         ┌────────────────────────────┐
│  Electron main             │         │  @slayzone/server          │
│   └─ embeds @slayzone/server         │  (plain Node process)      │
└────────────────────────────┘         └────────────────────────────┘
                  Local mode                       Remote mode
```

- One transport: tRPC v11 over WebSocket. No `ipcMain` in the long run.
- Domains compile + run under plain Node — zero `import 'electron'` in
  anything the server pkg pulls in.
- Renderer doesn't care which mode it's in. Same client, different URL.

## Migration principle

**No big-bang branch. Lift things over on `main`, one tiny batch at a time,
ship to production after each batch.**

The existing `phase-0-path-port-hardening` branch is a useful reference for
*what* the end state looks like, but we are **not** merging it. It diverged
too far. We re-derive the changes in small, independently-shippable slices
straight onto `main`.

Each batch must:

1. Be small enough to review + ship the same day.
2. Be behavior-preserving — no user-visible regression.
3. Pass typecheck, e2e, lint, prod build.
4. Be releasable on its own, even if nothing else lands after it.

## Lift-over slices (rough order, not a rigid plan)

These are the *shapes* of slices, not a numbered roadmap. Real batches will
be smaller and chosen opportunistically.

1. **Path + port hardening.** Honor `SLAYZONE_STORE_DIR`, `SLAYZONE_PORT`,
   `SLAYZONE_MCP_PORT`, `SLAYZONE_HOST`. Redirect `userData` early. Bind
   ports via helpers. No behavior change in default Electron mode.
2. **Transport pkg scaffold.** Add `@slayzone/transport`: empty tRPC v11
   appRouter + WS server, React client + provider, port bootstrap. No
   procedures yet.
3. **Per-router migration.** Migrate `ipcMain` handlers to tRPC routers
   one domain at a time (tags → projects → diagnostics → history → …).
   Each domain = one shippable PR. Both transports coexist until the
   domain is fully cut over.
4. **Domain split (server/ + electron/).** Inside each `packages/domains/*`,
   move pure logic into `src/server/`, leave Electron glue in
   `src/electron/`. Add static guard: `src/server/**` must not import
   `electron`.
5. **Renderer cutover.** Migrate components off `window.api.*` and onto
   tRPC hooks. Component-by-component. Preload bridge shrinks gradually.
6. **`@slayzone/server` package.** New package that imports every domain's
   `./server` entry, mounts the tRPC appRouter, starts the WS server.
   Runs under plain Node. Electron main becomes a thin wrapper that
   embeds it.
7. **Local/Remote toggle.** Settings UI for choosing embedded vs remote.
   Embedded supervisor (exp backoff, /health probe). RemoteConfigScreen
   fallback.
8. **Drop legacy IPC.** Once nothing calls `window.api.*` anymore, delete
   the preload bridge and the IPC handler registry.

## What stays Electron-only

Some features will never live on the server because they need the desktop
shell:

- WebContentsView browser panel
- Native menus, global shortcuts, tray
- File picker dialogs
- node-pty (server can do PTY too — but local terminal stays local in
  remote mode)

These stay in `src/electron/`. The server pkg simply doesn't expose them.
Renderer gracefully degrades or hides them when connected to a remote.

## Constraints / non-negotiables

- **Never drop existing functionality** to make a slice land. Migrate,
  refactor, preserve.
- **Each batch ships to prod.** If a slice can't be released cleanly,
  it's too big — split it.
- **Type safety end-to-end.** tRPC `AppRouter` type flows from server pkg
  to renderer.
- **Single source of truth per concept.** No parallel IPC + tRPC handlers
  living forever. Cut the IPC side as soon as the tRPC side ships.
- **Tests migrate with the code.** Unit + e2e tests follow each slice;
  e2e suite uses `getTrpcVanillaClient` instead of `window.api`.

## Open questions

- WS auth in remote mode — token? mTLS? defer to dedicated slice
- Multi-tenant DB layout — one sqlite per tenant vs shared Postgres
- Migration story for users with local data → hosted account
- node-pty in remote mode — allow shell access on the server host?
