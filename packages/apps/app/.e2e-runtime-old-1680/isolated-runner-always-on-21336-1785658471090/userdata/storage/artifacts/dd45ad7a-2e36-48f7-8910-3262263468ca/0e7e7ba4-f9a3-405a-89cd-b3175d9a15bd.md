# Meeting notes outline — Scenario B

Participants: **Kalle** (Facilitator, knows the truth), **Max** (Engineer), **Philip** (Engineer), **Sara** (CEO — only as a resource for the engineers, not driving the response).

Structured to walk the IR Plan stages: **Reporting → Severity → Triage → Investigation → Containment → Recovery → Hardening / post-mortem.** Times are indicative for a 1-hour run.

---

## 1. Event reported (0:00–0:03)

- Kalle reads the surface scenario aloud (from Section 2).
- One of the engineers claims the **Security Delegate** seat for the duration of the response — should emerge naturally from the conversation rather than being assigned. The other engineer joins as IRT.
- Sara confirms she has filed the **Security Event Report** in the system and pinged `#security`. She steps back; engineers run the floor.
- Security Delegate opens an incident ticket in Linear, links the Security Event Report, and starts a thread in `#security` for ongoing status.

## 2. Severity & escalation (0:03–0:07)

- Multi-customer availability impact → engineers discuss severity. IR Plan lists "system outages" under P2/P3 examples, but multi-customer + production-facing pushes this toward P1. Decision: **P1**.
- Per IR Plan for P1: documented + Slack notification to the appropriate manager. Sara is already in the loop; no further executive escalation needed unless scope changes.
- Security Delegate records severity in the Linear ticket.

## 3. Triage & analysis (0:07–0:15)

- Hypothesis space: frontend issue? Backend mutation? Worker stalled? LLM provider issue?
- First checks (split between Max & Philip):
  - Browser network tab on a repro: `createRun` mutation returns 200, then nothing. → rules out frontend / mutation layer.
  - Azure / app logs for the run IDs: only the `createRun` request appears; no `Starting extraction worker` lines. → worker is the suspect.
- Security Delegate updates the Linear ticket: "Frontend OK, worker not picking up jobs."

## 4. Investigation (0:15–0:30)

- Engineer A (Max): opens Bull Board. Sees `ExtractInsightQueue` is not paused but has no recent activity for the affected `extractionId`s.
- Engineer B (Philip): queries the DB for `ExtractionInsightResult` rows for one of the affected extractions:
  ```
  status = {"type":"WAITING"}
  updatedAt ≈ 3 hours ago
  ```
  A ghost row.
- Together they look at the **original job's last log line** for that ghost row → container OOM kill, exact timestamp matches `updatedAt`.
- Light-bulb moment: the `assertExtractionNotRunning` guard is silently blocking new runs because the prior row never transitioned out of `WAITING`.
- Sara is consulted only to confirm: "Any external comms needed yet?" → Security Delegate says hold; root cause is internal and contained to one extraction at a time.

## 5a. Immediate containment (0:30–0:38)

- One engineer manually transitions the stuck `ExtractionInsightResult` row to `CANCELED` (whoever has DB write access).
- Verify: a fresh Run Extraction on the affected extraction now starts; worker picks it up; status moves `WAITING → RUNNING → COMPLETED`.
- Repeat for any other extractions found stuck in the same state.
- **In parallel**, the Security Delegate drafts the customer-facing note for support to send to the two reporting customers ("We identified a stuck job blocking your runs and have cleared it. Please retry; we'll follow up with a write-up."). Sara approves tone. The note goes out while the second engineer continues verifying recovery — customer comms and remediation run concurrently, not sequentially.

## 5b. Containment ticket (0:38–0:42)

- Open a forward-looking Linear ticket so the same OOM tomorrow doesn't repeat the outage: extend `assertExtractionNotRunning` to treat rows older than a watchdog window as non-blocking (defence in depth at the guard layer). This is the *containment* fix — it stops the same root cause from producing the same outage again. Long-term hardening goes under step 7.

## 6. Recovery & breach assessment (0:42–0:48)

- Confirm customers' retries succeed end-to-end.
- GDPR / DPA check (per IR Plan): no PII processed during the failure, no unauthorised access → no IMY notification, no customer DPA notification trigger. Documented in the Linear ticket.
- Security Delegate marks the incident as **contained** in the Linear ticket.

## 7. Hardening & post-mortem (0:48–0:55)

- Open follow-up Linear tickets beyond the containment work in 5b:
  1. **Watchdog job**: auto-cancel `WAITING`/`RUNNING` rows older than N minutes (start with N = 60).
  2. **Alerting**: paging alert when ghost rows accumulate above a threshold.
  3. **Worker resilience**: figure out why the OOM exited without transitioning status; wrap the worker's main loop so an uncaught exit marks status `ERROR` before the process dies.
- Schedule a written RCA within 1 week per IR Plan ("A root cause analysis may be performed on all verified P1 security incidents"). Owner: Security Delegate.

## 8. Wrap (0:55–1:00)

- Recap action items, owners, and due dates inside the Linear ticket.
- Confirm the post-mortem meeting time.
- Kalle moves to the **follow-up questions** (Section 6) to capture exercise feedback.

## Notes for the facilitator

- **Play the system, not just the narrator.** Once the scenario has been set, your job during stages 3–6 is to be the oracle the engineers query. When they ask "what does Bull Board show for `ExtractInsightQueue`?" — answer with concrete numbers in the moment. When they ask "what's in `ExtractionInsightResult` for that extractionId?" — give them the ghost row. Don't volunteer information they didn't ask for; let them discover it.
- **Severity + breach assessment are deliberately formal this year.** Last year these were either glossed over (severity → "urgent") or skipped (no GDPR/DPA walk-through). They're in the IR Plan and represent a maturity step. If the team tries to skip either, prompt: "What severity is this?" and "Any data-protection implications to assess?"
- Keep the team out of "let's actually fix the bug now" mode — the exercise is about following the IR Plan, not eliminating the root cause in real time. Push back gently if they over-engineer.
- If they don't open a Linear ticket early, prompt: "Where are we tracking this?"
- If they jump straight to the database without checking logs first, let them — but during the post-mortem note that "logs first, DB second" is the cleaner sequence.
