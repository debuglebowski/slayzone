# Data Masking — Evidence Index

**Control:** ISO 27001:2022 **A.8.11 Data masking** · Vanta **DCH-111** · Normain

Sensitive data is protected by layered masking controls. Each file below is a screenshot captured from a **live system** — production logging (BetterStack) or the source repository on `main` — and reflects merged / deployed state.

| # | File | What it shows | Vanta evidence type |
|---|------|---------------|---------------------|
| 1 | `evidence-bullet1-codeql-no-customer-data-in-logs.png` | The CI-enforced CodeQL `NoCustomerDataInLogs` rule that blocks customer data / PII from being written to logs. | Config settings from data masking tools (custom scripts) |
| 2 | `evidence-bullet1-log-redaction-denylist.png` | The runtime redaction denylist (`REDACT_KEYS`) in the logging serializer — secret/credential fields are replaced with `[REDACTED]`. | Config settings from data masking tools (custom scripts) |
| 3 | `evidence-bullet1-secret-conceal-function.png` | `concealValue()` — obfuscates configuration secrets to `abc***xyz` before they are logged. | Config settings from data masking tools (custom scripts) |
| 4 | `evidence-bullet3-prod-logs-real-stream.png` | Live **production** log stream in BetterStack where the masked/concealed values are emitted. | Screenshots of masked data within logs |
| 5 | `evidence-bullet4-rbac-access-control.png` | Role-based access control (roles + permissions) restricting access to unmasked data to authorized users. | RBAC settings — only authorized users access unmasked data |
| 6 | `evidence-bullet6-masking-effectiveness-tests.png` | Automated tests asserting secrets are masked while non-sensitive fields (IDs, counters) are preserved — masked vs. unmasked. | Results of data masking effectiveness tests |

**Coverage:** Vanta acceptable-evidence bullets 1, 3, 4, and 6. Structured data (DB fields, integration secrets) is protected via field-level encryption and response masking; unstructured data (application logs) via the redaction/concealment controls above.
