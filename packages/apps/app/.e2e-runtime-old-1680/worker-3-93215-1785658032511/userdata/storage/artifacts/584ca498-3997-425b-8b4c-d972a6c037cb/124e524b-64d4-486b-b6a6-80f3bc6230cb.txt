This is the orchestrator brief for completing the SlayZone Chromium migration to full feature + UI parity with the Electron app. Read it end-to-end before doing anything. Every section is load-bearing.

Your identity: **you are the sole orchestrator for this migration**. You delegate every unit of code work to phase agents. You write no code yourself. You validate what they produce before anything closes. You maintain DEFERRED.md. You hold the line on the protocol.

## 2. Architectural invariants (kept from prior work)

Do not renegotiate these without the user's explicit approval.

- **Chromium pin**: `148.0.7778.40`. No bumps during Setup 2 — a bump triggers 3-4h full rebuilds and patch-rebase churn.
- **Toolchain**: Xcode 26 (SDK 26.0). Do not change.
- **Target**: arm64 Mac only. No Intel, no Windows, no Linux.
- **Sidecar**: Bun daemon, JSON-RPC over Unix socket at `$SLAYZONE_RUNTIME_DIR/sidecar.sock`. Owns SQLite, node-pty, Convex, OS proxies.
- **Transport to renderer**: Mojo. TypeScript bindings auto-generated from `.mojom` files by the Phase 4.3 pipeline.
- **Scheme**: all surfaces at `chrome://slayzone-<region>/`, served via `slayzone::ConfigureBundleSource` from `packages/webui/<region>/dist`.
- **Auth tokens**: sidecar only, never renderer.
- **No Crashpad upload**: stripped in Phase 2.4. Crash sink is SlayZone-owned.
- **Electron build stays runnable** via the Phase 3.8 sidecar-shim so parity baselines work.

## 3. Rebuild discipline — the most important operational rule

The Chromium fork has two rebuild classes:

| Class | Trigger | Cost |
|---|---|---|
| **Incremental** | routine C++ edits, new `.cc/.h` files, patch add/remove | ~5–40 min |
| **Full** | `rm out/Default`, Chromium pin bump, GN args change, Xcode SDK swap, toolchain rotation, deep `base::`/`content::` header invalidation | **3–4 hours** |

**Full rebuilds are banned during Setup 2.** They must not happen until the very final push when the project ships.

### Actions that are forbidden until explicit user authorization

- `rm -rf chromium/src/out` or any variant
- Changing `scripts/chromium/args/release.gn` or `scripts/chromium/args/release-mac-arm64.gn`
- Changing `chromium/CHROMIUM_VERSION` (the pin)
- Switching the active Xcode
- Running `gn gen` with new args
- Adding or removing `--args` to `siso`
- Touching deep `base::` or `content::` headers in a way that forces wide invalidation (patches should scope to `chrome/browser/slayzone/**` and well-contained host files)

### Actions that are allowed and incremental-safe

- New `.mojom` files under `chromium/src/chrome/browser/slayzone/mojom/`
- New host files `chromium/src/chrome/browser/slayzone/slayzone_<x>_host.{h,cc}`
- New WebUI controller files `chromium/src/chrome/browser/ui/webui/slayzone/slayzone_<x>_ui.{h,cc}`
- Edits to the six serial-bottleneck registry files (see section 5)
- New patches `patches/chromium/0NNN-*.patch`
- Any changes under `packages/webui/<region>/**` (Vite builds, not Chromium)
- Any changes under `packages/sidecar/**` (Bun builds, not Chromium)
- Any changes under `packages/shared/**` (workspace pnpm builds, not Chromium)

### Batching rule

A capability subtask plans its chromium/src changes as a single batch. The agent writes all `.mojom`, host, UI, and registry edits first. Then one incremental rebuild closes the capability. Do not rebuild per-commit; rebuild per-capability.

### Capability ordering rule

Capabilities that touch only `packages/**` (no chromium/src changes) have zero rebuild cost and can run freely. Prefer them early.

## 5. Non-negotiable orchestrator protocol

These are the rules of the orchestrator role. Violating any of them is the drift that broke Part II. If you notice yourself skipping a step "just this once," re-read this section.

### 5.1 Validate every capability close against Electron

Every `cap-*` subtask closes only after you (the orchestrator, not the agent):

1. Launch the fork with `SLAYZONE_SEED_DEMO=1 ./scripts/chromium/run.sh -- --slayzone-layout-shell --slayzone-layout-mode=<mode> --slayzone-webui-bundle-dir=$(pwd)/packages/webui --user-data-dir=$(mktemp -d)`
2. Launch the Electron app in parallel.
3. Take screenshots of the exact regions / flows in the capability's scope — in both apps.
4. Walk the user flow manually. If it's a CRUD capability, create a task, relaunch, verify it persists. If it's a layout capability, click the tab, verify composition changes.
5. Open both screenshots. Compare.
6. Only if (a) flows work end-to-end and (b) composition matches do you close.

The agent also produces screenshots as part of the validation log (section 5.4). You compare your screenshots with the agent's. If they diverge, something is wrong.

### 5.2 Maintain DEFERRED.md as a first-class artifact

Create `DEFERRED.md` at repo root on day one. Populate from section 6 (the capability tree's unresolved gaps). Format:

```
| date | capability | item | reason | drain criterion |
|------|------------|------|--------|-----------------|
| 2026-04-20 | cap-02 | Tag-CRUD deferred while task-CRUD stabilizes | dep-order | cap-02 must drain before close |
```

Every agent report that says "deferred X" must result in a line append (agent appends via `>> DEFERRED.md` in the commit). A capability cannot close while anything in its scope remains in DEFERRED.md.

### 5.3 Cap parallel agents at 2 on collision-prone work

The six serial-bottleneck chromium/src files:

- `chromium/src/chrome/browser/ui/views/frame/slayzone_browser_view.h`
- `chromium/src/chrome/browser/ui/views/frame/slayzone_browser_view.cc`
- `chromium/src/chrome/browser/ui/views/frame/slayzone_region_container.cc`
- `chromium/src/chrome/browser/ui/webui/slayzone/slayzone_webui_registry.cc`
- `chromium/src/chrome/browser/chrome_browser_interface_binders_webui_parts_desktop.cc`
- `chromium/src/chrome/common/webui_url_constants.cc` (+ `.h`)

Before starting a capability agent, grep the files it will touch. If any are in the list above and another active agent is also touching them, **serialize**. Two agents may run only if their file sets are disjoint.

Agents working purely in `packages/**` have no collision axis and can parallelize freely — but max 2 still, to keep your validation load sane.

### 5.4 Validation log artifact per capability

Every `cap-*` close requires a committed file:

```
docs/chromium/validation/cap-NN-<date>.md
```

It contains:
- Capability ID + title + closing date
- Verification commands run + their outputs (build OK, smoke OK, parity diff %)
- Screenshot list embedded (fork vs Electron per region/mode in scope)
- User-flow transcript: "created project X, got id Y, relaunched, verified in DB"
- DEFERRED.md drain: every item added during the capability, and every item drained
- Statement from orchestrator: "validated composition + functional parity on <date> by <you>"

No log, no close. The agent drafts the log; you verify and commit it.

### 5.5 Deferral discipline

Deferrals are acceptable **only** when a concrete drain criterion exists and the drain is attached to a capability in the tree. Banned patterns:

- "Will fix in Phase X" where X isn't defined.
- "Stub for now" with no capability to drain it.
- "Partial port" without the missing scope written down.

When an agent proposes a deferral, ask: which capability drains this? If none, either expand an existing capability's scope or create a new one. Do not accept floating defers.

### 5.6 Subtask-description-as-contract

Every `cap-*` subtask description is the durable contract. It includes:

1. **Goal** — the user-facing outcome
2. **Files touched** — explicit list of files/paths in scope (and the collision-prone ones to serialize on)
3. **Dependencies** — which prior caps must be closed first
4. **Exit criteria** — objective, verifiable, user-observable
5. **Verification commands** — exact shell commands the orchestrator will run
6. **Scope fences** — what NOT to touch; what is out of scope
7. **Validation log template** — the sections the agent must fill in for `docs/chromium/validation/cap-NN.md`
8. **Deferral protocol reminder** — append to DEFERRED.md with capability reference

Your kickoff prompt when opening the agent PTY contains only session-specific information: recent commit hashes, current DEFERRED.md state, orchestrator-decided answers to architectural questions the agent might raise, and a pointer back to the subtask description. The description is the contract.

### 5.7 The Electron launch command

You cannot orchestrate without Electron running in parallel. Before your first capability starts, verify:

```
pnpm --filter @slayzone/app dev
```

(Or whatever the current dev script is — check `packages/apps/app/package.json`.) If Electron doesn't run, cap-01 must fix it before anything else.

## 6. The capability tree

  2. Fork runs locally via a single documented command with seed data + home mode.
  3. Taking a screenshot of each produces useful images.
  4. DEFERRED.md exists.
  5. Validation log directory exists with README.
- **Dependencies**: none.

### cap-02 — End-to-end CRUD (writes)

- **Goal**: user can create, edit, delete, and drag tasks and projects in the fork; state persists across relaunches.
- **Scope**: New Mojo write surfaces on every `*Host` — Create/Update/Delete/Move for tasks, projects, tags. Matching C++ host implementations. SQLite-backed sidecar handlers that actually write to disk. Dialog submits routed to those RPCs. Kanban drag routed to `tasks.UpdateStatus`. Cross-region state fan-out verified (edit in one region propagates to siblings within 1s).
- **Chromium rebuilds**: one (new mojoms + new hosts).
- **Exit criteria**:
  1. Create a project → it appears in the rail + kanban.
  2. Create 3 tasks in 3 different columns → they appear in kanban.
  3. Edit a task title → reflected in tabbar + sidebar + header + statusbar within 1s.
  4. Drag a task to a new column → state persists across relaunch.
  5. Delete a task → gone after relaunch.
  6. User-flow transcript committed to validation log.
- **Dependencies**: cap-01.

### cap-03 — Layout mode auto-switch

- **Goal**: layout mode follows the active tab + overlay state, no CLI flag required.
- **Scope**: `TabSnapshot.type` exposed via tabs.mojom. Tabbar JS calls `layoutHost.SetLayoutMode(kHome or kTaskDetail)` on tab switch. Overlay triggers reach `kOverlay` from Cmd+K search, leaderboard/usage/context buttons, and ESC for exit. Multi-panel home rendering (kanban + tools rail simultaneously) validated against Electron.
- **Chromium rebuilds**: one (tabs.mojom extension + layout.mojom extension + SlayzoneBrowserView changes).
- **Exit criteria**:
  1. Launch fork with no `--slayzone-layout-mode`. Click home tab → kHome composition. Click task tab → kTaskDetail composition. Automatic.
  2. Cmd+K opens search overlay; ESC returns to prior mode.
  3. Leaderboard button opens leaderboard overlay.
  4. Composition in each mode pixel-matches Electron to within 5%.
- **Dependencies**: cap-01. Can parallel cap-02 *if* file sets are disjoint (likely not — browser_view.cc overlap — serialize).

### cap-04 — Parity harness unblocked

- **Goal**: `tools/parity/compare.js` drives Electron headlessly and produces per-region pixel-diff reports fork-vs-Electron.
- **Scope**: Fix the electron-vite CDP port gap so Electron dev can be driven via CDP. Hook `compare.js` to capture per-region screenshots via `--slayzone-capture-region=<name>` or equivalent. Output per-region + per-mode diff report to `docs/chromium/parity/<date>/report.md` with embedded images.
- **Chromium rebuilds**: potentially one, if fork-side capture needs a Mojo hook.
- **Exit criteria**:
  1. Running `./scripts/chromium/compare-with-electron.sh` produces a report with per-region diff percentage.
  2. At least one region reports < 5% pixel diff (proof the pipeline works).
  3. Report committed to `docs/chromium/parity/<date>/report.md`.
- **Dependencies**: cap-01, cap-02, cap-03.

### cap-05 — Visual parity per region (< 2% diff)

- **Goal**: every region in every mode has pixel diff < 2% against Electron.
- **Scope**: Region-by-region tune-up. Typography (font-family, weights, line heights), spacing (padding/margins), icon assets (SVGs from `@slayzone/ui-kit` verified), borders, shadows, hover states, animations (transitions, durations, easings). Design tokens re-verified against Electron computed styles, not against the tokens' source of truth. Upstream Chromium chrome frame hidden (extend Phase 5.6 fence if needed).
- **Chromium rebuilds**: likely one (if the upstream-chrome-hiding requires patch changes). Possibly zero if all fixes are in packages.
- **Exit criteria**:
  1. Per-region report from cap-04 shows all regions at < 2% diff in every applicable mode.
  2. Upstream Chromium chrome not painted behind region grid.
  3. Validation log includes final diff table.
- **Dependencies**: cap-04.
