# AI Provider Tycoon — Implementation

Locked technology and architecture decisions. The "how we build it" companion to the design assets (1–5).

## Stack

- **Runtime:** Bun
- **Backend / persistence:** Convex (reactive DB, real-time subscriptions)
- **LLM provider abstraction:** Vercel AI SDK (runs on the **client**, not the server)
- **Realtime / live UI:** WebRTC (spectator streams, peer-to-peer where applicable)

## Architecture — client-driven

Most of the loop runs on the player's client. Server is a thin authority + relay. Trade-off: trivial server cost, BYOK keys never touch our infra; downside is no protection against malicious clients (intentionally accepted for v0.1).

### Client responsibilities
- Schedule its own ticks against a **shared wall clock** (all clients fire at the same epoch-aligned interval).
- Snapshot local state, call its own LLM via Vercel AI SDK (BYOK).
- Validate the response client-side; drop illegal actions.
- POST validated actions to the server, tagged with the target tick number.
- Subscribe to server broadcasts to update local state.

### Server responsibilities
- Generate **situations** authoritatively (server owns the situation event sequence).
- Accept incoming action POSTs, **rate-limited per client** (one tick's worth at a time).
- Resolve each tick: apply collected actions + situation effects against the pre-tick state, emit new events.
- Append events to Convex; broadcast via reactive subscription.
- Pre-match: verify match config, lock prompts, draw the seed.

### Things explicitly not handled
- Sync guarantees. Slow client → drops actions / misses ticks. Their problem.
- Malicious clients. No proof-of-work or signature checks on POSTs.
- Connection quality. No reconnection retries, partial-state catch-up, or backfill.

## Tick loop

**Wall clock**, e.g. every 60s on the dot, all clients aligned.

### Client, on each tick boundary
1. Snapshot local view of state.
2. Call own LLM with prompt + snapshot + schema.
3. Validate response locally; drop illegal actions.
4. POST actions to server, tagged with tick number.

### Server, on each tick boundary
5. Generate situations for this tick (event-sourced, deterministic from prior log).
6. Collect client actions for this tick (rate-limited).
7. Resolve simulation step atomically: apply all actions + situation effects against pre-tick state.
8. Append events to Convex log.
9. Broadcast event slice to all clients.

### Client, after broadcast
10. Apply broadcast events to local state.
11. Wait for next clock boundary.

### Late actions
If a client POSTs after the server has resolved that tick, the action is rejected. Client's loss.

## Replay model

Replay = pure event log playback. **All randomness is captured as events** when it occurs (situation fires, sabotage rolls, etc.) — there is no RNG re-derivation on replay. An event log is sufficient to reconstruct any past state.

This means: no need for seeded sub-PRNGs or determinism plumbing. The log *is* the source of truth.

## Failure handling

Graceful error messages, no special treatment per failure type.

- Player API key revoked / errors out → that tick's POST simply doesn't arrive; treated as a no-op. No elimination, no special status.
- Server transient error → retry on next tick boundary.
- Client disconnect → resumes from event stream when it reconnects.

## Match config

- **Default player count:** 4
- **Max player count:** 8
- **Default tick interval:** 60s (configurable per match)
- **Default rounds:** 100 (configurable per match)
- **Scenario:** AI Provider (hardcoded for v0.1; no scenario abstraction layer).

## Lifecycle

### Pre-match
- Server validates match config (player count, rounds, tick interval).
- Each client pings its own API key locally before joining (Vercel AI SDK trivial call).
- All prompts locked client-side, hash committed to server.
- Match seed drawn server-side, written to log.

### Post-match export
At match-end: serialize the full event log + final state snapshot to a single JSON bundle. One zip per match. Sufficient for v0.1 "scrub the log" replay.

## Testing

### Stub agents
For CI / smoke tests without API costs:
- `random` — uniform legal action choice each tick.
- `idle` — emits no actions.

Drive the tick loop with stubs in tests; reserve real BYOK calls for live matches.

## Observability

### Per-tick decision log
Each inference is recorded as an event:

```
{
  tick,
  player_id,
  raw_response,          // full string from provider
  parsed_actions,        // validated action list
  validation_errors,     // illegal actions dropped
  request_duration_ms,
  token_usage            // {input, output}
}
```

Replay viewer is **deferred** — v0.1 ships JSON export only; build a UI in v0.2 if matches are fun enough to scrub.

## GUI (throwaway)

UI surface follows from the data — backend exposes the events and current state, frontend assembles whatever view is convenient. Not a design concern for v0.1.
