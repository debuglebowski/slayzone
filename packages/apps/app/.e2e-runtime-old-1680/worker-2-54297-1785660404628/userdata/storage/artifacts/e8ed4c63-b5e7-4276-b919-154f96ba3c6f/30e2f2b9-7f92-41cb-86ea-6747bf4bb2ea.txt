# Meeting notes
Kalle facilitated and also acted as the system, answering the responders' queries about logs, dashboards, and database state as they investigated. Notes follow the stages of the Incident Response Plan.
### Reporting & kickoff (14:45)
Kalle set the scene: two customers, within five minutes of each other, reported that pressing Run Extraction on a run page does nothing — the button shows its loading state and never returns a result, with no error on screen. Sara, as CEO, had already logged a Security Event Report and flagged it in #security.
Philip volunteered to take the Security Delegate role for the incident; Max joined as the second responder. Sara stepped back and said she would stay reachable if the team needed a decision or sign-off.
Philip opened an incident ticket to track the response, linked Sara's Security Event Report, and started a status thread in #security so the rest of the company could follow along.
### Severity (14:49)
Max and Philip talked through severity. The Plan files outages under the lower P2/P3 band, but both noted this was hitting multiple customers at once on a core production feature, with the blast radius still unknown. They agreed to treat it as P1 and revisit if it turned out to be isolated.
Philip recorded P1 on the ticket and, per the Plan, pinged the responsible manager in Slack. Sara was already aware, so no further escalation was needed for now.
### Triage (14:52)
The team laid out where the failure could live: the front end, the Run Extraction action itself, the worker that processes runs, or the model provider downstream.
Max reproduced it on a run page — pressing Run Extraction returned 200 with no client-side error, but no insights ever appeared. That pointed away from the front end and the request layer.
Philip pulled the Azure application logs for the affected run IDs. He saw the Run Extraction action being received, but none of the extraction-worker-starting lines that should follow.
Philip: "The action goes through but nothing runs. Whatever's wrong is between the request and the worker."
He noted the working theory on the ticket: front end fine, jobs not being processed.
### Investigation (14:57)
Max opened Bull Board to look at the queues.
Max: "Kalle — on Bull Board, what does ExtractInsightQueue look like? Is it paused?"
Kalle (as the system): "Not paused, it's running. But there's no recent activity for the extractions you care about — nothing's moved through for those in hours."
A live but idle queue. Max flagged that as odd: if jobs were being enqueued, something downstream should be consuming them.
Philip went to the database and looked at the ExtractionInsightResult rows for one of the affected extractions.
Philip: "What's the status on the rows for this extraction?"
Kalle (as the system): "One row sitting in WAITING. Its updatedAt is about three hours old."
Philip: "Three hours — so it's been parked there the whole time, nothing's touched it."
Max connected it to the guard:
Max: "If there's already a row in WAITING, the new-run check refuses to start another one. That's assertExtractionNotRunning — it reads the old row as still in-flight and silently blocks every new attempt. That's why the button does nothing and there's no error."
To find out why the original row never finished, Philip pulled that job's worker logs around the updatedAt timestamp.
Philip: "Kalle — last log line for that original job?"
Kalle (as the system): "The container was OOM-killed. The timestamp matches the row's last update almost exactly."
That closed the loop: the original job died on an out-of-memory kill mid-run, never wrote a terminal status, and left the row frozen in WAITING. The guard then treated that ghost row as an in-flight run and blocked everything new for that extraction.
Philip checked in with Sara on whether anything external was needed yet. She asked whether customer data had been exposed or lost; the team confirmed it had not — this was a stuck job, not a data issue — so she agreed there was nothing to report externally at this stage and asked to be kept posted.
### Containment — immediate (15:10)
Max manually moved the stuck row to CANCELED. Philip kicked off a fresh Run Extraction on the same extraction to verify.
Kalle (as the system): "New run starts. Worker picks it up — WAITING, then RUNNING, then COMPLETED. Insights come back."
Fix confirmed for that customer. The team then checked whether other extractions were wedged the same way and cleared the few they found.
In parallel, Philip drafted a short note for support to send the two reporting customers: we found a stuck job blocking your runs, we have cleared it, please retry, and we will follow up with a brief write-up. Sara read it over and approved the tone. The note went out while Max kept verifying recoveries — comms and remediation ran at the same time rather than one waiting on the other.
### Containment — preventing a repeat (15:20)
The team agreed that clearing rows by hand was not a fix. Philip opened a single follow-up ticket: stop a stuck row from blocking new runs by having the guard disregard stale rows, and add alerting so the next occurrence is caught before customers notice. That stops the same OOM tomorrow from reproducing today's outage.
### Recovery & data-protection check (15:26)
Max confirmed the reporting customers' retries completed end to end.
Per the Plan, the team walked the data-protection angle explicitly: no personal data was processed or exposed during the failure, and there was no unauthorised access — the jobs simply did not run. Conclusion: no IMY notification and no customer DPA notification triggered. Philip recorded that assessment on the ticket so the reasoning is on file.
Philip then marked the incident contained.
### Wrap (15:42)
Philip recapped the follow-up ticket and its owner, then Kalle closed the scenario portion and moved the group into the exercise-feedback questions (captured under Discussion & Conclusions).
