# Could the tar cluster (#50, 52, 59, 73, 100, 102) be risk-accepted like prisma?

**Short answer**: Yes, technically — but the argument is **weaker** than the prisma case, and the fix is **cheap enough** that risk-acceptance is the wrong tool here. Recommend fixing.

## The two cases compared

| Aspect | Prisma / effect (#110) | Tar cluster (#50, 52, 59, 73, 100, 102) |
|---|---|---|
| Vulnerable code path | Effect Rpc + AsyncLocalStorage under concurrency | Tarball extraction (path traversal, symlink/hardlink poisoning, Unicode race) |
| Reachability in our deployment | **Not reachable** — `@prisma/config` never invokes Rpc/ALS | **Reachable** — tar IS invoked when `@mapbox/node-pre-gyp` extracts canvas's prebuilt binary |
| Input source | n/a (path not invoked) | canvas project's GitHub release artifacts (signed tarballs) |
| Execution timing | n/a | Install-time only (yarn install / CI build); never at runtime |
| Trust boundary | n/a | Trusted publisher (canvas maintainers), HTTPS download, lockfile checksum |
| Compensating controls | Code-path not exercised + Dependabot | yarn.lock integrity SHA512, npm registry signing, install-time-only, no production runtime exposure |
| Argument strength | **Strong** ("not reachable") | **Moderate** ("reachable but with strong supply-chain controls") |

## Why the tar argument is moderate, not strong

The vulnerable tar code path **is** invoked — every time `yarn install` rebuilds canvas's native bindings, node-pre-gyp downloads and extracts a tarball using the vulnerable `tar@6.2.1`. This isn't a "code present but never called" case like prisma.

To exploit, an attacker would need to:

1. Compromise canvas's GitHub release artifacts, OR
2. Compromise the npm registry's tarball serving, OR
3. MITM the install (defeated by HTTPS), AND
4. Bypass the integrity SHA512 checksum stored in `yarn.lock`

This is a real supply-chain attack scenario — not unprecedented (`event-stream`, `colors.js`, `node-ipc`). And blast radius isn't zero: tar path-traversal at install time can write files outside `node_modules/`, potentially modifying CI/dev machine state. It does NOT affect production runtime (the prebuilt binary is what ships, not tar's extraction logic).

So the argument shape is:

> "Vulnerable code is reachable, but with strong compensating controls (lockfile integrity, trusted publisher, install-time-only, no runtime exposure). Residual risk is supply-chain compromise of `canvas`."

That's a defensible **Medium**-rated risk acceptance, not a strong one. Auditors may push back, especially given:

- 6 alerts (visual weight in Vanta dashboard)
- Oldest is **102 days** (#50 from 2026-01-16) — long-standing high severity
- ISO 27001:2022 A.8.8 specifically calls out timely patching of known vulnerabilities

## But more importantly: the fix is cheap

Unlike prisma v7 (a real ORM migration), the tar fix is a **one-line resolution**:

```jsonc
// root package.json
"resolutions": {
  "@mapbox/node-pre-gyp": "^2.0.3"
}
```

Then `yarn install` and run `root:test` + a fresh canvas rebuild check.

Why this is low-effort:

- `@mapbox/node-pre-gyp@2.0.3` uses `tar^7.4` (patched line)
- `node-pre-gyp` is install-time only — its API surface for callers (canvas) is small and stable across 1.x → 2.x
- Failures (if any) surface immediately on `yarn install` in CI, not as runtime bugs
- No application code changes
- Estimated effort: 30 min including PR + CI run

## Recommendation

**Don't risk-accept the tar cluster.** Just fix it.

The prisma case was different because:
1. The remediation cost was high (major ORM upgrade)
2. The exploitability argument was strong ("path not reachable")

The tar case inverts both:
1. Remediation cost is low (single resolution line)
2. Exploitability argument is moderate (reachable, but with controls)

When the fix is essentially free, you spend less compliance capital fixing it than you do justifying the deferral. Save risk-acceptance for cases like prisma where the trade is genuinely worth it.
