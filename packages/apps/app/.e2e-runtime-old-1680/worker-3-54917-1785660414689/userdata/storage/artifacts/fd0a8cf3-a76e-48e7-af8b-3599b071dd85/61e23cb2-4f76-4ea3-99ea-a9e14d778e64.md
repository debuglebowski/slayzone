# Electron Migration Investigation

## Context

Current pain: browser panels inlined clunkily. No Chrome extension support.

## Clarification

Electron **is** Chromium. Uses same V8+Blink as Chrome. "Migrate to Chromium" ambiguous — four distinct directions:

1. **Stay on Electron, unlock Chrome extension API** (Electron supports `session.loadExtension` — MV2 full, MV3 partial since Electron 37+)
2. **Swap to different Chromium wrapper** (CEF, Qt WebEngine)
3. **Fork Chromium directly** (Brave/Arc/Vivaldi/Edge model)
4. **Leave Chromium entirely** (Tauri/WKWebView/native = *less* extension support, not more)

## Chrome extension support — detail

| Runtime | MV2 | MV3 | Notes |
|---|---|---|---|
| Electron | yes | partial (service workers since 37, declarativeNetRequest since 40) | `session.defaultSession.loadExtension(path)` |
| CEF | yes | partial | Same Chromium subset |
| Fork Chromium | yes | yes (full) | Own build = Chrome parity |
| Tauri (WKWebView/WebView2/WebKitGTK) | no | no (WebView2: limited preview only) | System webviews don't load ext |
| Safari WKWebView | no | no | Safari has own ext model |
| Real Chrome (embed via CDP) | yes | yes | Launch real Chrome, puppeteer-style |

**Key insight**: Electron already closest to full Chrome extension support of any embeddable engine. Forking Chromium is only path to 100% parity. Tauri/WKWebView = **regression**, not improvement.

## Resource reality

RAM per Electron `WebContentsView` ≈ new Chromium renderer proc (~80-150 MB base). Tauri saves RAM only on Mac/Linux where system WebKit already loaded. Win Tauri still spins WebView2 proc (~Chromium). **Real wins on Mac only.**

## Four rational paths

Main pain = Chrome extensions. **Only Chromium-based runtimes give this.** Tauri/WKWebView = dead end for extension goal. CEF = same ceiling as Electron + massive rewrite cost.

### Path 1: Stay Electron, invest in extension UX

- Wire `session.loadExtension`, build extension-store UI
- Effort: days–weeks
- Ceiling: MV2 full + MV3 ~80%
- Risk: low

### Path 2: Embed real Chrome via CDP

- Launch user's Chrome, control via `chrome-remote-interface`, render into native window via CDP tiles or separate window
- Full extensions (user's)
- Effort: weeks
- Risk: fragile, Chrome auto-updates break CDP surface
- Requires user has Chrome installed

### Path 3: Fork Chromium

| Aspect | Detail |
|---|---|
| What | Clone Chromium source, patch, ship own browser binary embedding SlayZone UI as chrome:// page or Chrome app shell |
| Extensions | Full MV2+MV3, Web Store compat |
| Effort | Months-years initial, ongoing merge pain |
| Build | 50-100 GB src, 2-8hr builds, needs `depot_tools`, `gn`, `ninja` |
| Maint | Merge upstream every 4 wks (Chrome release cadence) or fall behind on security patches |
| RAM | Same as Electron (it's Chromium) |
| Distribution | Ship own ~200 MB installer per platform |
| Team size req | Historically 3-10+ engineers dedicated (Brave ~30, Arc ~15, Vivaldi ~25) |
| Examples | Brave, Arc, Vivaldi, Edge, Opera, Comet, Dia |

#### Fork vs embed-Chrome-via-CDP

| | Fork Chromium | Embed real Chrome (CDP) |
|---|---|---|
| Extension support | Full, native | Full via user's Chrome |
| Control | Total (patch anything) | Zero over Chrome internals |
| User needs Chrome installed | No | Yes |
| Maint burden | Huge (upstream merges) | Low (Chrome auto-updates) |
| Risk | Security lag if behind | Chrome updates break CDP surface |
| Binary size | +200 MB | +0 MB |

#### Why typically rejected for small teams

- Chrome ships every 4 wks. Miss merge window → stale security patches → CVE exposure
- CI/CD needs beefy machines (64+ GB RAM, 100+ GB disk per agent)
- Single-engineer fork = unsustainable within 6-12 months

#### Why worth considering for SlayZone

- AI coding assist → merge pain maybe tractable (agent handles conflicts)
- Full extension support = goal met absolutely
- Own whole stack → no Electron ceiling ever again
- Could bundle own agent-native extensions out of box

### Path 4: Accept ceiling, move to Tauri for RAM

- Abandon extension goal
- Gain 60-70% RAM savings Mac/Linux
- Rewrite Rust main
- Effort: months

## Unresolved questions

- Which extensions matter? (1Password? uBlock? Dashlane? DevTools ext?) — determines if MV3 partial enough
- RAM budget hard constraint or nice-to-have?
- Win/Linux users? (kills WKWebView option)
- Willing to rewrite main proc Rust/C++? (kills CEF/Tauri if no)
- Fork maint burden acceptable w/ AI assist? (kills/keeps Path 3)
- Distribution model change OK? (Chrome-embed path needs user's Chrome present)
