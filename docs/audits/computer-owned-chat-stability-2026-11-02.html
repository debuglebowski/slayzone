P1F01 · Data loss reproduced on disposable copiesA restored hub backup can activate empty history+
Trigger
Create a normal hub backup while ownership is legacy or copying, with no completed destination. Restore that snapshot, then run normal migration.
Observed
Backup sanitation removed the only source events while keeping the pending locator. Both hub and computer accept active ownership, epoch 2, with cleanup complete and zero original events.
Why
Backup sanitation deletes all legacy content regardless of whether durable computer ownership exists. Restore has no proof that its now-empty source lost data.
Repair
Prevent publication of a supposedly recoverable snapshot that strands pending content. Preserve a valid transition recovery source or fail backup explicitly; reject empty cutover when required source proof is missing. Keep the post-cutover hub content-free.

P1F04 · Both normal reads and migration retries stay blockedAn attachment edit can permanently strand migration+
Trigger

Observed

What held up

  • Ten lost-reply/restart checkpoints recover through serialized real endpoints: metadata freeze, transfer begin/chunks/finish, verification, attachment upload and activation reply.
  • Trash → prepared transfer → reconnect → undo preserves draft, revision and bytes.
  • Permanent deletion defeats older hub state, valid old activation proof and a later active lifecycle revision.
  • Retention defers actual prepared/Trash content across restart while pruning unrelated cold history.
  • Wrong scope, duplicate file entries, missing database and corrupt listed blobs reject restore without damaging earlier readable archives.
  • Connector replacement preserves terminal PID; offline hook capture/replay, multi-provider prompt capture and strict protocol controls pass. New remote computer identities cannot appropriate old ownership.

Recommended repair order

Make backup and restore fail safely

F01 + F03 + F11 · keep transition data recoverable, reconcile prepared proofs, validate archive completeness.

Complete recovery before normal metadata traffic

F02 + F07 · explicit state matrix for every hub/computer pair; activate committed destinations before metadata; normal operations choose active stores.

Freeze versions and cover every content-bearing identity

F04 + F05 + F06 · immutable manifest inputs, sealed embedded refs, migration census independent of current tab mode.

Repair storage/UI distinction and backup availability

F08 + F09 + F10 · prompt stores stay invisible; preserve later user activity during repair; show actual failures; incomplete transfers do not disable healthy backups.

Bound control-path work, then rerun release gates

F12 + F13 · SQL projections/indexed seeks, all 43 audit cases green, fresh upgrade/restore/reconnect replay, byte-level corpus checks and UI/device coverage.

Unresolved implementation questions: exact transitional backup policy and reviewed repair of already-generated tabs. Recommended constraints: no silent empty restore, no loss of existing content, no weakening of active-owner/deletion fences.
